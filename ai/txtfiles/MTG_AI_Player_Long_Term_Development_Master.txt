0. PROJECT PURPOSE
======================================================================

PROJECT NAME
-------------
Working name: MTG AI Player
Possible future product names:
- ManaMind
- StackMind
- Planeswalker AI
- ManaBrain
- SpellSense
- Priority
- Arcane Engine
- DuelMind

CORE VISION
-----------
Build a serious artificial intelligence system that can learn to play
Magic: The Gathering at a high level.

The project is NOT intended to begin as:
- a chatbot that recommends cards
- a simple "best play" LLM wrapper
- an Arena bot made by clicking pixels
- a deck recommendation website

The long-term goal is to build a real game-playing intelligence.

The ideal final system should be able to:

1. Represent a complete MTG game state.
2. Understand legal game actions.
3. Search through possible future game states.
4. Handle hidden information and uncertainty.
5. Evaluate board states and strategic positions.
6. Learn from self-play and/or recorded games.
7. Model different opponents and play styles.
8. Make decisions at multiple levels of abstraction.
9. Explain decisions in understandable language.
10. Analyze human games and identify mistakes.
11. Eventually play against humans.
12. Eventually become a sellable MTG training/product platform.

IMPORTANT PHILOSOPHY
--------------------
Build the underlying technology first.

Do not optimize for flashy UI early.
Do not build monetization before the core engine is credible.
Do not depend on an external LLM for the fundamental game-playing logic.
Do not attempt all of Magic at once.

The most important asset is the game engine + AI environment + training
pipeline. Everything else can be built around it later.

======================================================================
1. WHAT MAKES MAGIC DIFFICULT FOR AI
======================================================================

Magic is an unusually difficult game for an AI because it combines:

- enormous card variety
- hidden information
- randomness
- imperfect information
- timing and priority
- the stack
- triggered abilities
- replacement effects
- continuous effects
- combat decisions
- resource management
- bluffing
- sequencing
- long-term planning
- rapidly changing board states
- interactions between cards
- multiple possible legal actions
- different objectives depending on deck and game state

This means the project should NOT treat MTG as a normal board game.

A useful mental model is:

CHESS
------
Mostly:
known state -> choose move -> new state

MTG
---
partially observed state
      +
large action space
      +
random events
      +
opponent hidden information
      +
rules engine
      +
strategic planning
      +
tactical response

Therefore, the AI architecture should eventually combine:

- rules engine
- action generation
- state evaluation
- search/planning
- probability
- opponent modeling
- machine learning
- memory
- natural-language explanation

======================================================================
7. PRIORITY AND THE STACK
======================================================================

THIS IS ONE OF THE MOST IMPORTANT SYSTEMS.

Do not write priority logic as scattered if-statements.

Create a dedicated priority subsystem.

Basic conceptual flow:

1. Game reaches priority point.
2. Active player gets priority.
3. Player may:
   - cast spell
   - activate ability
   - take special action
   - pass
4. If action is taken:
   - cost is paid
   - targets selected
   - object added to stack
   - priority resets according to rules
5. Players continue passing.
6. If all players pass:
   - top object resolves
7. State-based actions checked.
8. Triggers placed on stack.
9. Priority begins again.

The engine must NEVER accidentally "skip" a legal response window.

8. ACTION REPRESENTATION
======================================================================

Every AI decision should eventually be represented as an Action object.

Example conceptual structure:

Action
------
type:
- CAST_SPELL
- ACTIVATE_ABILITY
- ATTACK
- BLOCK
- PLAY_LAND
- PASS_PRIORITY
- SPECIAL_ACTION

data:
- card ID
- ability ID
- targets
- mana payment
- attackers
- blockers
- selected mode
- X value
- additional choices

An action must be:

1. uniquely representable
2. serializable
3. replayable
4. validated by the rules engine
5. reversible or reproducible for simulation

This becomes critical for search.

======================================================================
9. GAME STATE SNAPSHOTS
======================================================================

AI search requires the ability to create hypothetical futures.

Therefore:

GameState -> clone -> apply action -> GameState'

Do NOT mutate the live game during hypothetical search unless the engine
supports safe transactional rollback.

Preferred early approach:

Immutable or snapshot-based state transitions.

Later optimization may use:
- copy-on-write
- incremental state
- reversible moves
- memory pooling

But correctness comes first.

======================================================================
10. RANDOMNESS
======================================================================

All random events should come from a centralized RNG system.

Examples:
- shuffle
- random discard
- random target
- random reveal
- random token choice

The random generator should accept a seed.

Every game should be reproducible from:

GAME SEED
+
INITIAL DECKS
+
PLAYER ACTIONS

This is incredibly valuable for debugging.

Example:

Game ID:
839174

Seed:
1293819281

When a bug occurs, save the seed and action sequence.

Then reproduce exactly.

======================================================================
14. SEARCH
======================================================================

Magic's action space can become huge.

Suppose:
- 8 cards in hand
- 10 permanents
- 6 abilities
- multiple targets
- multiple attackers
- multiple modes

The number of possible actions can explode.

Therefore AI search needs:

ACTION PRUNING
--------------
Remove obviously useless actions.

Examples:
- illegal actions
- redundant actions
- dominated actions
- irrelevant target combinations

ACTION GROUPING
---------------
Treat equivalent actions similarly where possible.

HIERARCHICAL ACTIONS
--------------------
Instead of immediately deciding every click:

LEVEL 1:
What is the plan?

LEVEL 2:
What category of action?

LEVEL 3:
Which card?

LEVEL 4:
Which target?

LEVEL 5:
Which exact mode/payment?

This can drastically reduce search complexity.

15. MONTE CARLO TREE SEARCH
======================================================================

Potential structure:

ROOT
 |
 +-- Action A
 |     |
 |     +-- Opponent response
 |     +-- Opponent response
 |
 +-- Action B
 |
 +-- Action C

MCTS cycle:

1. Selection
2. Expansion
3. Simulation
4. Evaluation
5. Backpropagation

For MTG, simulations must account for hidden information.

Therefore eventually use:

Information Set MCTS
or another imperfect-information search approach.

Early version:
Simple rollout with deterministic/random opponent behavior.

Later:
Opponent-aware probabilistic simulation.

======================================================================
16. VALUE FUNCTION
======================================================================

The AI eventually needs to answer:

"How good is this position?"

Possible target:

V(state) = probability of winning from state

Example:

State A:
V = 0.73

State B:
V = 0.41

This is much more useful than simply:

"Board score = +4"

because it directly relates to winning.

However, intermediate auxiliary predictions can improve learning:

- win probability
- expected future life
- probability of lethal
- card advantage
- board control
- mana advantage
- estimated opponent hand interaction
- probability of drawing outs

19. SELF-PLAY
======================================================================

A simple self-play cycle:

1. Agent A plays Agent B.
2. Record complete trajectory.
3. Determine winner.
4. Store:
   state
   action
   legal actions
   reward
   hidden information
5. Train model.
6. Evaluate new model.
7. Promote if stronger.
8. Repeat.

Potential problem:
Both agents can learn the same bad strategies.

Solution:
Maintain diverse opponents.

Population:

Aggro
Control
Midrange
Combo
Tempo
Random
Old versions
Heuristic
Specialized anti-meta agents

This creates more robust training.

20. REWARD DESIGN
======================================================================

PRIMARY REWARD
--------------
Win:
+1

Loss:
0 or -1

But pure win/loss rewards can be sparse.

Potential auxiliary signals:

- damage dealt
- life preserved
- mana efficiency
- card advantage
- board development
- successful interaction
- lethal avoidance

IMPORTANT:
Auxiliary rewards can create bad behavior.

Example:
If you reward life too strongly, an AI might become excessively passive.

Therefore:
Win probability should remain the central objective.

The AI must distinguish:

OBSERVABLE:
- opponent battlefield
- visible graveyard
- life
- tapped lands
- revealed cards
- known commander

HIDDEN:
- opponent hand
- unknown library
- unrevealed cards

The AI should maintain a belief distribution.

Example:

Control

Known cards:
Counterspell

Unknown hand:
Potentially:
- 35% removal

- 20% unknown

These probabilities should update after every observation.

======================================================================
23. BLUFFING
======================================================================

A strong MTG AI should eventually understand that a card's value can
come from what the opponent THINKS you have.

Example:

You have no counterspell.

You leave two mana untapped.

Opponent may believe you have one.

This creates strategic value even though no spell was actually cast.

The AI therefore needs to reason about:

"What does my opponent think I have?"

And:

"What does my opponent think I will do?"

This eventually becomes recursive reasoning.

30. LLM ROLE
======================================================================

LLM SHOULD NOT BE THE CORE DECISION MAKER.

Good uses:

- explain AI decisions
- answer rules questions
- summarize games
- teach concepts
- generate practice exercises
- communicate with players
- convert technical evaluation into natural language

Bad use:

Send entire game state to an LLM and ask:

"What should I do?"

Problems:
- unreliable
- expensive
- inconsistent
- limited precise search
- hard to reproduce
- difficult to train
- not ideal for huge action spaces

The LLM is the INTERFACE/TEACHER.

The game-playing model is the PLAYER.

A game AI is only as good as the simulator.

A subtle bug in the engine can train the AI on fake Magic.

Therefore every rule subsystem needs tests.

Examples:

- damage

- lifelink
- indestructible
- trample
- first strike
- double strike
- flying
- ward
- hexproof
- protection
- counters
- copying
- replacement effects
- triggers
- sacrifice
- discard
- draw
- exile
- zone changes

======================================================================
32. TESTING STRATEGY
======================================================================

Use several layers of testing.

UNIT TESTS
----------
Test individual rule components.

INTEGRATION TESTS
-----------------
Test interactions between systems.

SCENARIO TESTS
--------------
Create complete known game situations.

PROPERTY TESTS
--------------
Randomly generate states/actions and check invariant rules.

REGRESSION TESTS
----------------
Every bug becomes a permanent test.

EXAMPLE REGRESSION TEST
-----------------------
Bug:
A creature was incorrectly able to attack immediately.

Test:
Creature enters under a player's control this turn.
Attempt attack.
Expected:
Illegal unless haste.

This bug should never return.

======================================================================
33. ENGINE INVARIANTS
======================================================================

Examples:

- A card instance can only exist in one zone at a time.
- A card cannot simultaneously be in hand and battlefield.
- Mana cannot become negative.
- A player cannot have impossible life values unless an effect allows it.
- A spell that has resolved should not remain on the stack.
- A permanent cannot have an invalid controller.
- A target must satisfy targeting restrictions when selected.
- Illegal actions must never reach resolution.

Add assertions aggressively during development.

Thresholds should be adjustable and validated.

73. WHEN YOU GET STUCK
======================================================================

Use this procedure:

1. Reproduce the problem.
2. Make a minimal test case.
3. Inspect the exact game state.
4. Identify which subsystem is responsible.
5. Write a regression test.
6. Fix it.
7. Verify thousands of random games.
8. Document the lesson.

Never fix a complex bug only by adding another special case.

Ask:
"Why did the architecture allow this bug?"

======================================================================
74. WHEN THE AI MAKES A BAD PLAY
======================================================================

Do not immediately change the model.

First determine:

Was the rules engine correct?

Was the action generator complete?

Was the action encoded correctly?

Was the state encoded correctly?

Was hidden information handled correctly?

Was search deep enough?

Was the value function wrong?

Was the training target wrong?

Was the opponent model wrong?

Was exploration too high?

Only then modify the AI.

Otherwise you may "fix" symptoms while preserving the real problem.
